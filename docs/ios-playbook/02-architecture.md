# Architecture

## Shape of the app

- **Native SwiftUI**, iOS 17+, iPhone only to start (iPad deferred, not dropped). Swift Concurrency (`async`/`await`) throughout.
- **MVVM.** Views are thin; view models are `@MainActor final class … : ObservableObject` and hold all state and derivation; models are plain value types.
- **No backend of our own** unless a feature truly needs one. The app talks straight to the data API. That rules out true push notifications, which was an accepted, recorded trade-off.
- **A hand-written `URLSession` client** instead of a networking library: one struct with one method per endpoint.

Folder layout under the app target:

```
App/          entry point, Info.plist
Models/       Decodable API types and pure derived values (e.g. MatchAnalytics, PlayerSeasonStats)
Networking/   the API client, response cache, small single-purpose clients
Persistence/  on-device stores (followed teams, pins, bundled directory)
Services/     multi-step work that isn't UI state (calendar export, match-sheet loader)
ViewModels/   one per screen
Views/        one folder per tab or feature; Shared/ for components
Theme/        design tokens
Resources/    assets, fonts, bundled data, String Catalogs
```

## Dependency injection, so everything is testable

Every view model, store and service takes its dependencies through its initializer, with production defaults:

```swift
init(relGUID: String, name: String, api: VBLAPIClient = .shared,
     loader: MatchSheetLoader? = nil, now: @escaping () -> Date = Date.init)
```

- The API client takes a `URLSession` and a cache, so tests pass a mock session and a temp-directory cache.
- Stores take a `UserDefaults`, so tests use a throwaway suite.
- Anything time-dependent takes a `now` closure.
- Anything debounced takes the debounce interval, so tests pass `.zero`.

`static let shared` singletons exist for the app's own wiring, but never reach for one *inside* a type you test. Inject it.

**Pitfall:** a view model that holds another `ObservableObject` as a plain stored property doesn't re-render when that object changes. Forward its `objectWillChange` in `init`, or have the view observe it directly.

## Networking

- **One client, one method per endpoint**, returning decoded model types. The HTTP shape (GET with a query, or PUT with a JSON body) stays inside the client.
- **Build request bodies with `JSONSerialization`**, never string interpolation.
- **Decode leniently where the API is sloppy.** A single unexpected `null` or changed type must not abort a whole array. Use `decodeIfPresent` with sensible fallbacks for fields that have been seen to vary, and write a regression test for each such case found live.
- **Normalize identifiers** before comparing if the API is inconsistent (collapsing whitespace in GUIDs, for example).
- **Concurrency limits:** when a screen needs many calls (a season of match sheets), run them in a `TaskGroup` with a fixed cap (4 here), report progress, and treat a failed item as "missing", never as fatal.
- **Polling:** only while the screen is visible, at the server's advertised cadence.

## Caching and offline

- A plain **file-based cache of the last successful raw response per key**. On a network failure the client serves the cached copy, and screens show a "last updated" time.
- **Cache-first for immutable data.** A finished game's sheet never changes, so it's served from cache without a request. An *empty* cached result isn't trusted, since it may still be filled in later.
- **Never cache responses that carry personal data** (see 01), and prove it with a test.

## Persistence

- Small user state (followed teams, pins) lives in **`UserDefaults` as JSON-encoded arrays**, in a store per concept. No accounts, no Keychain, no database until something needs one.
- Keep separate concepts in separate stores, even when they look alike: "follow" (drives Home and Agenda) and "pin" (a Stats bookmark) are different things.
- **Bundled reference data** (a club/team directory) when the API has no search or list endpoint. It's compiled offline by a script in `tools/`, shipped in `Resources/`, and refreshed by re-running the script.
- Stores honour a **UI-test reset launch argument** (`--uitest-reset-state`) by skipping their load for that launch. Don't clear `UserDefaults` and read it straight back this early in launch: it races the cache.

## Generated Xcode project

- The project is generated by **XcodeGen** from `ios/project.yml`. The `.xcodeproj` is gitignored. Run `xcodegen generate` after adding or removing files, or after changing `project.yml`.
- `project.yml` holds the targets, bundle ID, deployment target, `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`, signing team and build settings, all reviewable in diffs.
- Set `SWIFT_EMIT_LOC_STRINGS: YES` and `LOCALIZATION_PREFERS_STRING_CATALOGS: YES`. Without them, Xcode extracts localization keys from source without type information, so `\(count) points` becomes `%@` instead of `%lld` and silently stops translating.
- If Xcode Cloud is used, `ci_scripts/ci_post_clone.sh` must install XcodeGen and generate the project, because the bare clone has none.

## Design system

- **Tokens in one file** (`Theme.swift`): background layers, text levels, an accent, semantic win/loss colours, a fixed home/away pair. Every view uses tokens, never literal colours.
- **Fonts:** a bundled display face (registered via `UIAppFonts`, referenced by PostScript name) for headlines and numbers, and the system font for body text, always through helpers that scale with Dynamic Type.
- **Check contrast in tests.** A unit test asserts the text tokens clear 4.5:1 against their backgrounds.
- **Reuse components** (rows, section headers, banners, segmented controls, location buttons) instead of restyling per screen. New features get their own small component file when they need more.

## Localization

- **Dutch is the development language and English the second.** Keys are the Dutch source text.
- **Use `LocalizedStringKey` for UI text parameters, not `String`.** A `String` parameter bypasses the catalog even when the call site passes a literal. Use `Text(verbatim:)` for data (names, scores) that must never be looked up.
- **Use plural variants** for any string with a count, or rephrase so no count needs a noun ("Games with stats: 3").
- **Check for missing translations mechanically.** The compiler's `.stringsdata` output lists the exact runtime keys; diff them against the catalog before release. A `LocalizationTests` file asserts that the important keys resolve in English.

## Accessibility

- Dynamic Type everywhere; layouts switch from horizontal to stacked at accessibility sizes, and pinned headers stop pinning.
- VoiceOver labels on every status element (results, live state, scores); combine row contents into one element, but keep interactive children (a Maps button) separate so they stay reachable.
- Selection state via `.accessibilityAddTraits(.isSelected)`, which UI tests can assert on too.
